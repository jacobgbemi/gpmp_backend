# Reporting Data Model

- **Status:** Architectural baseline
- **Date:** 2026-10-05

## Purpose

This document defines how GlintPM Private should organize data for dashboards, project reports, management reporting, and project-controls analysis.

Reporting data should remain traceable to authoritative operational records.

## Reporting flow

```text
Authoritative Operational Data
          ↓
Validated Calculations
          ↓
Reporting Model / Aggregates
          ↓
Dashboard / Report / Export
```

## Reporting dimensions

Common dimensions may include organization, project, reporting period, data date, schedule, baseline, activity, cost category, responsible party, risk category, change category, and status.

## Reporting facts

### Schedule performance

Potential facts: planned value, forecast dates, actual dates, duration, progress, variance, and critical-path indicators.

### Cost performance

Potential facts: budget, commitments, actual cost, forecast cost, variance, and currency.

### Progress

Potential facts: planned progress, actual progress, period progress, and cumulative progress.

### Risk

Potential facts: risk count, score, exposure, open/closed status, and mitigation progress.

### Change

Potential facts: change count, requested value, approved value, schedule impact, and implementation status.

## Reporting periods

Reports should use an explicit reporting period or data date so results can be reproduced for a defined point in time.

## Baseline comparison

Performance reporting should distinguish current actual/forecast values from an identifiable approved baseline.

## Derived metrics

Derived metrics require documented formulas, source fields, units, and rounding rules before becoming authoritative KPIs.

Examples include schedule variance, cost variance, Schedule Performance Index, Cost Performance Index, forecast variance, and progress variance.

## Snapshot strategy

For high-value reporting, consider snapshots or period summaries so historical reports do not unexpectedly change when current operational records are edited.

Example:

```text
Project
Reporting Period
Data Date
Baseline Reference
Actual Metrics
Forecast Metrics
Variance Metrics
Generated At
Generated By
```

## Operational vs reporting models

Operational data should optimize correctness and transactional workflows. Reporting structures may optimize aggregation and dashboard performance. Any denormalized reporting structure must document its source of truth and refresh strategy.

## Scaling

Potential strategies, in increasing complexity, include optimized indexes, precomputed aggregates, materialized views, scheduled reporting jobs, dedicated reporting tables, and separate analytical storage.

## Data freshness

Dashboards/reports should expose data freshness when it matters, for example:

```text
Data Date: 30 Sep 2026
Generated: 02 Oct 2026 14:30
```

## Tenant isolation

Every reporting query must preserve organization boundaries. Cross-organization reporting requires explicit platform-level authority.

## Auditability

Important reports should retain enough metadata to establish reporting period, data date, baseline reference, calculation/version where applicable, generation time, and requesting user.

## Implementation note

Actual reporting tables, views, aggregation jobs, dashboard queries, and KPI formulas must be verified against the repository.
